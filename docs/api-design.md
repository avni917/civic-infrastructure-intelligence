# API Design

## 1. Purpose

This document defines the planned REST API for Civic Infrastructure Intelligence.

The API will allow the frontend to authenticate users, submit and retrieve reports, manage incidents, assign repair teams, update incident statuses, and retrieve analytics.

The endpoints listed here are planned interfaces. They should be implemented and tested incrementally.

## 2. API Conventions

- Base URL during local development: `http://localhost:8000/api/v1`
- Communication format: JSON for standard requests and responses.
- Authentication: A secure token or session mechanism, as configured by the backend.
- File uploads: Multipart form data where appropriate.
- Identifiers: Unique database-generated identifiers.
- Timestamps: ISO 8601 format, stored consistently in UTC.
- Errors: Consistent JSON error responses with appropriate HTTP status codes.

The API documentation generated by FastAPI will be available through its interactive Swagger UI, typically at `/docs` on the running development server.

## 3. Authentication Endpoints

### POST /auth/register

Registers a new citizen account.

Example request:

```json
{
  "name": "Sample Citizen",
  "email": "citizen@example.com",
  "password": "example-password"
}
```

Expected behavior:
- Validate the submitted fields.
- Check that the email is not already registered.
- Hash the password securely.
- Create the account with the default citizen role.
- Never allow public registration to create an administrator account.

### POST /auth/login

Authenticates a registered user.

Expected behavior:
- Verify credentials.
- Return the configured authentication result.
- Reject invalid credentials without exposing sensitive details.

### GET /auth/me

Returns the authenticated user's profile and role.

## 4. Report Endpoints

### POST /reports

Creates a citizen report.

The request will contain a category, description, latitude, longitude, and an optional photograph. If a photograph is included, the request will use multipart form data.

Expected behavior:
- Validate category, description, and geographical coordinates.
- Validate uploaded file type and size.
- Save the report.
- Initiate or queue duplicate detection.
- Return the created report and its initial processing state.

### GET /reports

Returns a paginated list of reports.

Possible query parameters:

- `page`: Page number.
- `limit`: Number of results per page.
- `category`: Filter by category.
- `status`: Filter by current incident or report status where applicable.
- `mine`: Restrict results to the authenticated user's reports, subject to the API's authorization design.

### GET /reports/{report_id}

Returns the details of an individual report that the requesting user is authorized to access.

### GET /reports/{report_id}/related-incidents

Returns the incident associated with the report and any relevant duplicate-matching information permitted for that user.

## 5. Incident Endpoints

### GET /incidents

Returns incidents visible to the authenticated user.

Possible query parameters:
- `category`
- `priority`
- `status`
- `department_id`
- `ward`
- `page`
- `limit`

### GET /incidents/{incident_id}

Returns incident details, including linked reports, location, priority factors, assigned department, assignment information, and status history according to the user's permissions.

### POST /incidents/{incident_id}/review-duplicate

Submits an authorized review decision for a proposed duplicate match.

Example request:

```json
{
  "related_incident_id": 42,
  "decision": "confirm_duplicate",
  "remarks": "Both reports describe the same pothole."
}
```

Allowed decisions will be explicitly defined by the implementation, for example `confirm_duplicate` and `not_duplicate`.

The system must validate that both incidents exist and that the requester has permission to review them. Merging incidents must preserve report associations and history.

### POST /incidents/{incident_id}/recalculate-priority

Recalculates an incident's priority using the current configured scoring rules.

This operation will be restricted to authorized users or trusted backend workflows.

## 6. Department and Team Endpoints

### GET /departments

Returns the available departments.

### GET /teams

Returns teams visible to the authenticated user, optionally filtered by department and availability.

### GET /teams/{team_id}

Returns team information and relevant operational details according to the requester's permissions.

### POST /incidents/{incident_id}/assign

Recommends or assigns a team to an incident, depending on the operation's implementation and the requester's permissions.

Example request:

```json
{
  "team_id": 7,
  "assignment_mode": "manual",
  "remarks": "Assigned after officer review."
}
```

The backend must validate team suitability, department compatibility, and assignment permissions. The exact request fields may change when automatic allocation is implemented.

### GET /incidents/{incident_id}/assignments

Returns the assignment history for an incident.

## 7. Status and Verification Endpoints

### PATCH /incidents/{incident_id}/status

Updates the incident status.

Example request:

```json
{
  "status": "IN_PROGRESS",
  "remarks": "Repair work has started."
}
```

Possible status values will be defined centrally. A proposed workflow is:

`OPEN → TRIAGED → ASSIGNED → IN_PROGRESS → RESOLVED → CLOSED`

Additional states such as `REOPENED` or `AWAITING_VERIFICATION` may be included in the final implementation.

The backend shall validate allowed transitions and record the old status, new status, timestamp, and responsible user.

### POST /incidents/{incident_id}/resolution-evidence

Submits resolution notes and optional repair evidence.

Expected behavior:
- Verify the user's permission.
- Validate uploaded files.
- Store evidence securely.
- Record the submission in the incident history.

### POST /incidents/{incident_id}/feedback

Allows an authorized citizen to provide feedback on an incident.

Example request:

```json
{
  "rating": 2,
  "is_resolved": false,
  "comments": "The damaged road surface is still present."
}
```

The backend shall validate the rating and feedback fields and apply the configured reopening or review rules.

## 8. Analytics Endpoints

### GET /analytics/summary

Returns high-level dashboard metrics, such as:
- Total reports.
- Total distinct incidents.
- Open and high-priority incidents.
- Overdue incidents.
- Resolved incidents.
- Reopened incidents.
- Average or median resolution duration, where sufficient timestamps exist.

### GET /analytics/category-distribution

Returns incident counts grouped by category.

### GET /analytics/trends

Returns incident counts over a selected time interval.

### GET /analytics/hotspots

Returns aggregated geographical information for identifying recurring issue areas.

The response must avoid exposing private citizen information. Hotspot calculations and thresholds will be documented as part of the implementation.

## 9. Example Error Response

```json
{
  "detail": {
    "code": "INVALID_STATUS_TRANSITION",
    "message": "The requested status change is not allowed."
  }
}
```

The final error format should be consistent across the application.

## 10. HTTP Status Codes

| Status | Meaning |
|---|---|
| 200 | Request succeeded |
| 201 | Resource created |
| 204 | Request succeeded with no response body |
| 400 | Invalid request or business-rule violation |
| 401 | Authentication required or invalid |
| 403 | Insufficient permissions |
| 404 | Resource not found |
| 409 | Resource conflict |
| 422 | Request validation failed |
| 500 | Unexpected server error |

The implementation should use appropriate codes consistently.

## 11. API Security Requirements

- Protected endpoints must require authentication.
- Role and resource-level authorization must be enforced by the backend.
- Users must not be able to update incidents merely by guessing identifiers.
- Public responses must exclude passwords, private tokens, and unnecessary personal information.
- Uploads must be validated and stored safely.
- Sensitive errors must not reveal internal implementation details.
- Administrative actions and important workflow changes must be auditable.

## 12. Implementation Order

1. Authentication and current-user endpoints.
2. Report creation and retrieval.
3. Incident listing and detail retrieval.
4. Status updates and history.
5. Department and team retrieval.
6. Assignment operations.
7. Duplicate review and priority recalculation.
8. Resolution evidence and feedback.
9. Analytics and hotspot endpoints.

## 13. Documentation Maintenance

When an endpoint's method, path, request schema, response schema, permissions, or behavior changes, this document and the relevant tests should be updated.
